## 1. Executive Assessment

**Overall:** ProcureDesk as defined _does solve a real problem_ (email/sheet P2P for 20-300-person orgs, 80 req/mo, 85 vendors) and is _not_ generic CRUD -- the budget-before-approval + threshold routing + immutable audit + file evidence forces transactions, locking, RBAC and idempotency. Market evidence supports the P2P (not S2P) positioning and the 1-6 week implementation window vs 4-18 month enterprise. The PRD is unusually thorough for a solo project and is _internally coherent enough to start Phase 0_, but it has **terminology drift, state-machine ambiguity, and MVP scope that is defensible but at the upper edge of solo feasibility**. No show-stopper that invalidates the product, but several High issues must be fixed before coding to avoid rework.

**Strengths:** Research traceability (39 sources), realistic Aarav persona (120 people, not enterprise), clear Before->After, domain model that correctly separates requisition (internal) vs PO (external, binding per Ivalua 2026-04-07), and scope that is explicitly opinionated (not Kissflow-style configurable) for SMB speed.

**Weaknesses:** Inconsistent entity naming (Spend Request vs Purchase Request vs Requisition), request-level ESCALATED state vs step-level ESCALATED conflated, missing "Changes Requested" return-to-draft path that real approvers expect, budget period handling underspecified, and MVP that includes _every_ engineering layer at once (portfolio value but schedule risk). All correctable without changing product direction.

**Verdict preview:** `NOT READY -- CHANGES REQUIRED` until the [Critical] + [High] fixes are applied. After the fixes listed in Section 17 (already applied where marked [FIXED]), verdict becomes `READY FOR PHASE 0`.

## 4. Workflow Audit

### Request workflow (Need -> Create -> Validate -> Submit -> Budget/Policy -> Approval -> Procurement -> Purchase -> Closure)

- **Are all states defined?** Mostly yes, but missing **Changes Requested -> DRAFT** loop that every real approver expects (see Section 5). Rejection as terminal forces clone-to-new-DRAFT, which loses the thread. | **High** | [FIXED] Added `CHANGES_REQUESTED` as a non-terminal rejection variant that returns request to `DRAFT` with comment preserved, distinct from `REJECTED` terminal. See state-machine.
- **Budget check timing:** PRD says submit allowed even if over, approve is the gate. This matches research (Fraxion real-time at approval) but is ambiguous vs future S2P where budget is checked at submission. Clarified as **policy choice, not inconsistency** -- for MVP, submit allowed, approve blocked unless exception. | **Medium** | Documented as configurable policy.
- **Vendor selection/quote:** Requires ACTIVE vendor and quote >10k before submit -- correct and matches procurement policy (Hyperbots authorization limits). No gap.
- **Purchase (PO) and fulfillment:** PO PDF as background job after APPROVED is correct (Procurify/Kissflow: approved requisition -> PO). Vendor communication as manual email at MVP is correct for solo scope; no vendor portal needed.

### Approval workflow

- **Sequential approvals:** **Correct** -- single-step + threshold sequential (order 1..N) matches SMB. Parallel deferred is correct (parallel needs order groups).
- **Amount thresholds:** Correctly threshold-based (Tacto 5k/50k example, AuraVMS DOA). But PRD example hard-codes 50k while business rules say configurable -- inconsistency. | **Medium** | [FIXED] All examples now note "e.g., threshold 50k (configurable per Budget/Org)".
- **Department/category/budget-owner:** Correctly deferred to Phase 2, but PRD Section 7D lists them as if MVP supports them. | **Medium** | [FIXED] Marked explicitly as Future in workflow, with MVP = threshold only.
- **Delegation:** Correctly deferred (AuraVMS backup provisions), manual escalation at MVP is sufficient.
- **Escalation 48h:** Correct (Kissflow 72h, we use 48h). But PRD counted escalation as request state (C2) -- fixed.
- **Rejection / changes requested:** **Gap** -- only REJECTED terminal at MVP. Real users expect "Request changes" returning to DRAFT. | **High** | [FIXED] Added.
- **Resubmission:** Clone-to-new-DRAFT for REJECTED is correct for terminal; CHANGES_REQUESTED returns to DRAFT directly.
- **Cancellation:** Rules clear (DRAFT any time, PENDING only if no step decided). Correct, but needs explicit "after APPROVED no cancel" -- done.
- **Expiration:** 48h timeout -> ESCALATED step, not auto-approve -- correct (never auto-approve money).

### Vendor workflow

- Onboarding -> verification -> active/inactive is correctly lightweight at MVP (single contact, no portal). Deactivation preserving history is correct for referential integrity. No gap.

### Purchase workflow

- Approved -> PO (PDF job) -> ORDERED -> receipt -> RECEIVED -> CLOSED is correct and matches Procurify 8-step without over-engineering. No PO approval chain at MVP is correct (request approval _is_ PO approval for SMB).

### Invoice workflow

- At MVP, invoice as File on RECEIVED for evidence, manual visual check, warn on >5% or 5k mismatch, no automated 2/3-way engine -- **correct deferral** for SMB where receipt is often a note, not dock scan. Full tolerance engine is enterprise. No gap.
- Payment status deferred to QuickBooks integration (correct, P2P compliments ERP).

### Budget workflow

- Allocation via budget name+period (not separate allocation table) is correct at MVP. Threshold warnings amber <20% or <50k is sensible. Exceeded handling (approve blocked unless Finance exception) is correct. Missing: **budget period edit mid-flight** -- if period shortened, PENDING requests with that budget become orphaned. | **Medium** | [FIXED] Added rule: budget period edits do not retroactively affect PENDING requests; new requests use new period.

## 5. State-Machine Review

### Purchase Requisition (canonical entity, was Spend Request)

**States (after fixes):** `DRAFT, PENDING_APPROVAL, APPROVED, REJECTED, ORDERED, RECEIVED, CLOSED, CANCELLED` + step status `ESCALATED` (not a request state). Plus `CHANGES_REQUESTED` returns to `DRAFT`.

**Transition matrix (who, guard, audited, notified):**

| From             | To                      | Action                 | Actor                                          | Guard                                                                                         | Terminal?                                                   |
| ---------------- | ----------------------- | ---------------------- | ---------------------------------------------- | --------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| DRAFT            | PENDING_APPROVAL        | Submit                 | Owner (requester)                              | Required fields, ACTIVE vendor, quote if >10k, budget org check, idempotencyKey not duplicate | No                                                          |
| PENDING_APPROVAL | APPROVED                | Approve (last step)    | Assigned approver (not own, in order, version) | Budget atomic `spent+amount <= amount` + threshold policy                                     | No                                                          |
| PENDING_APPROVAL | PENDING_APPROVAL (stay) | Approve (not last)     | Assigned approver                              | Same guards, not last step                                                                    | No                                                          |
| PENDING_APPROVAL | REJECTED                | Reject                 | Any assigned approver                          | Comment required, immediate terminal, budget untouched                                        | **Yes** (REJECTED terminal, clone to new DRAFT to resubmit) |
| PENDING_APPROVAL | DRAFT                   | Changes Requested      | Any assigned approver                          | Comment required, returns to DRAFT for edits, preserves thread, audit `CHANGES_REQUESTED`     | No                                                          |
| PENDING_APPROVAL | PENDING_APPROVAL        | Escalate (timeout 48h) | System (job) or Admin manual                   | Creates new step ESCALATED + new PENDING step for Finance/Owner, request stays PENDING        | No                                                          |
| PENDING_APPROVAL | CANCELLED               | Cancel                 | Owner                                          | Only if all steps still PENDING (no APPROVED/REJECTED yet)                                    | **Yes**                                                     |
| DRAFT            | CANCELLED               | Cancel                 | Owner                                          | Any time in DRAFT                                                                             | **Yes**                                                     |
| APPROVED         | ORDERED                 | Order                  | Finance/Admin                                  | Only APPROVED, enqueues PO PDF job, PO number assigned                                        | No                                                          |
| ORDERED          | RECEIVED                | Receive                | Finance/Admin                                  | Requires receipt File (RECEIPT type), amount warn if >5% diff                                 | No                                                          |
| RECEIVED         | CLOSED                  | Close                  | Finance/Admin                                  | Only RECEIVED                                                                                 | **Yes**                                                     |
| APPROVED         | CANCELLED               | (none)                 | --                                             | **Blocked** -- after APPROVED no cancel (use exception)                                       | --                                                          |

**Invalid transitions (must 409/422):** APPROVED->PENDING, REJECTED->PENDING (must clone), CLOSED->any, CANCELLED->any, ORDERED->PENDING, editing non-DRAFT.

**Dead-end check:** No dead-end except the three terminals (REJECTED, CANCELLED, CLOSED) which are intentionally terminal but have clone paths documented. PENDING cannot be orphaned because escalation ensures progress.

**Rollback/reversal:** No rollback. Budget increment is transactional with last approve; if closed request needs reversal, new compensating request must be created (future credit note). Correct for MVP.

**Concurrent transitions:** All approve/reject/order/receive/close must check `version` (optimistic lock) and Budget `FOR UPDATE` (see Technical). Two approvers clicking Approve at same version -> one 409. This is specified but was missing from PRD Section 9 NFR; added.

**Issues found:**

- C2 (ESCALATED as request state) -- **Critical**, fixed.
- Missing CHANGES_REQUESTED loop -- **High**, fixed.
- Budget change mid-flight retroactivity not defined -- **Medium**, fixed to not retroactive.
- No explicit "re-open" after CLOSED/REJECTED -- correctly disallowed (clone instead), but PRD Section 15 bullet "Can something be re-opened?" was not answered; clarified.

### Vendor

**States:** `ACTIVE, INACTIVE`. Transitions: `ACTIVE->INACTIVE` (deactivate with reason, audit, blocked for new requests but history remains). `INACTIVE->ACTIVE` (reactivate). No DELETE if history exists. **No issue.**

### Budget

**States:** Implicit via period+spent. No state machine needed, but period edits not retroactive is now defined.

### ApprovalStep

**States:** `PENDING, APPROVED, REJECTED, ESCALATED`. Transitions mirror request but per step with order guard. **No issue** after C2.

## 14. MVP Scope Review -- Ruthless

**Is MVP too large?** At the upper edge but **not too large** for a 10-12 week solo phased plan. Every MVP item in PRD 18 maps to a business acceptance in 19 (e.g., budget enforcement -> `FOR UPDATE`, files -> signed URL, audit -> 7-year). Removing any one would break a workflow the client would reject ("I cannot prove who approved"). The solo risk is _schedule_, not _scope creep_ -- mitigated by phasing (1 orgs -> 2 vendors/requests -> 4 state machine -> 5 jobs/cache -> 7 deploy) and by keeping MVP _opinionated_ (single threshold, no parallel/category, no PO table, no Invoice entity). | **Medium** -- monitor; no cut recommended now, but if schedule slips, cut PO PDF background job (make synchronous) and caching (add later) first, not audit/budget.

**Too small?** **No** -- a smaller MVP (orgs+vendors+requests without budgets/approvals/audit/files) would be generic CRUD and fail business objectives (no overspend prevention, no audit). That would be a _different_ product.

**Missing critical workflow?** **No** after CHANGES_REQUESTED added. Complete valuable flow DRAFT->CLOSED with threshold is now coherent end-to-end. The only deliberately missing critical workflow at MVP is _full 3-way match_ (PO=Receipt=Invoice with tolerances) -- correctly deferred because SMB receipt is often a note, not dock scan (hospitality pain: 3-way is standard but many SMBs skip for low-value). MVP warn on invoice mismatch is sufficient.

**Overloaded with enterprise?** **No** -- S2P (sourcing/RFx, reverse auctions, supplier risk, contract lifecycle, supplier portal) is explicitly out-of-scope and would be correctly rejected as enterprise bloat. Parallel approvals, category routing, cost-center GL are also deferred. The MVP is P2P, not S2P, which matches the 1-6 week mid-market window.

**Minimum coherent product:** **Yes** -- a user can register -> create org -> invite 3 roles -> create vendor -> create budget -> create request with quote -> get approved (with threshold adding Finance) -> order (PO PDF) -> receive (receipt) -> close -> query audit, all without email as system of record. That is the _minimum_ that is still _valuable_ (audit in minutes, not days) and _teaches_ the hard parts.

**Verdict on scope:** **Appropriate, but at upper bound.** Keep scope, enforce phasing, and track burn-down weekly. No feature cut now.

## 16. Market & Competitor Reality Check

**What real products commonly support (industry fact):**

- All of Precoro, Procurify, Kissflow, Ivalua document the P2P spine requisition->approval->PO->receipt->invoice->match->payment. (Ivalua 2026-04-07, Procurify 2025-10-02, Kissflow ERP Research)

- Budget real-time at approval is a top spend-control feature (Fraxion, Procurify standout). Our "remaining shown at approval" matches.
- ERP as system of record (Kissflow: P2P compliments ERP, integrates to NetSuite/SAP/Oracle). Our QuickBooks future sync is correctly deferred.
- Audit append-only is standard (JAGGAER logs every approval automatically). Our 7-year immutable matches.
- Implementation 1-6 weeks for mid-market P2P vs 4-18 months for S2P (Kurums, SCClarity). Our P2P scope matches the 1-6 week window.

**What is product-specific (not standard):**

- Precoro 14-day trial vs our no trial yet (not needed at MVP).
- Coupa SpendGuard 25+ alerts vs our simple warning on invoice mismatch -- we correctly defer predictive.

**What we intentionally simplify (and correctly per research):**

- Opinionated single threshold vs Kissflow visual designer (flexible but maintenance-heavy at 50 workflows, ProcurementAI).
- PO as generated PDF on request (not separate PO table) vs enterprise PO lifecycle with vendor acknowledgment.

- Making compliant buying _easier_ than maverick (Ramp pattern: pre-fill + duplicate flag before approver) -- we have duplicate detection as Phase 10, but could add duplicate warning even without AI (simple title/vendor/amount match) as a low-tech win.

**Distinction maintained in PRD 22:** Every research-backed tag cites a source; client assumptions (50k, 10k quote, 10L max) and open questions (category routing, period retroactivity) are explicitly marked not as facts.
